# Самостоятельный эмулятор и встроенный режим

Эта папка содержит собственный сервер, UI, состояние и protobuf-схемы.
Её можно скопировать отдельно от прокси, в том числе переименовать.
Внешние сервисы для запуска не требуются.

## Запуск из этой папки

```powershell
python -m pip install -e ".[test]"   # из корня репозитория
python -m server_emulator.server
```

Адрес, порты и сертификат — state/server.json («Дополнительно → Сервер»), аргументы `--host`, `--port`,
`--ssl/--no-ssl`, `--cert`, `--key`, `--http-port` перекрывают файл.
Собственный каталог данных: `python -m server_emulator.server --state D:/my-emulator-state`.
Тестовый экземпляр без портов колонок: `python -m server_emulator.server --host 127.0.0.1 --port 18090 --no-ssl --http-port 0`.

UI: http://127.0.0.1:8877/emulator/
HTTP/WS устройства обслуживаются на том же порту; для UniProxy используется /uni.ws.
Чтобы принимать подключения по сети: `python -m server_emulator.server --host 0.0.0.0 --port 8877`.
Для HTTPS/WSS: `python -m server_emulator.server --port 8878 --cert cert.pem --key key.pem`.

## Встраивание в прокси (временно)

Проход к настоящим серверам у эмулятора собственный — `server_emulator/upstream/` (режимы маршрута устройств). Раздел «Эмулятор» открывает тот же UI и тот же Runtime. Переключатель
«Проксирование / Эмуляция» применяется к новым HTTP-запросам и WS-соединениям.
Существующие WS-соединения сохраняют прежний обработчик до переподключения.
По умолчанию сохраняется проксирование. В эмуляции неизвестный endpoint возвращает
404; автоматического fallback на Яндекс нет. Эмулированный обмен записывается
в журнал прокси с emulated=true.

Standalone всегда обслуживает эмуляцию. Поле mode в settings.json управляет только
встраивающим прокси; standalone его не использует для пересылки запросов.
По умолчанию обе формы используют state/ этой папки. Для одновременно работающих
независимых экземпляров задавайте разные --state: настройки загружаются при запуске,
горячая синхронизация между процессами пока не реализована.

## Из трафика в обработчик

1. В прокси открыть запрос, выбрать response_original или response_sent.
2. Нажать «В эмулятор · обработчик».
3. Открывается UI эмулятора с новым выключенным черновиком.
4. Отредактировать название, host/method/path/status, body_json или body_base64,
   проверить содержимое и включить обработчик.
5. Переключить прокси в эмуляцию либо скопировать эту папку со state/ на другой сервер.

JSON-ответ после импорта можно редактировать. Gzip JSON распаковывается;
бинарные ответы сохраняются как base64 вместе с Content-Encoding.
Cookies и транспортные заголовки не импортируются. Тела могут содержать приватные
данные исходного устройства, поэтому state/ исключён из Git.
Сопоставление HTTP — по домену, методу и пути без query, последний подходящий
включённый обработчик имеет приоритет. Поддержаны доменные aliases в settings.json.

Для WS импортируется серверное AAPI-сообщение. В черновике нужно указать trigger
(входящий Event, например TextInput) и отредактировать message (protobuf JSON).
При отправке Event обновляются MessageId и RefMessageId. Это один ответ на триггер,
не произвольная последовательность всего записанного диалога.

## Модель, речь и инструменты

«Модель и промпт»: полный URL операции Chat Completions, модель, API-ключ,
температура, системный промпт, контекст устройства. Включённые схемы tools
передаются модели как function tools. API-ключи в GET UI/API маскируются;
локально settings.json хранит их в открытом виде.

«Инструменты / MCP»: JSON HTTP initialize → notifications/initialized → tools/list,
затем tools/call. При обнаружении инструменты выключены, имена получают префикс
сервера. Поддержан JSON-ответ HTTP MCP; SSE и stdio пока не подключены.
Если сервер возвращает nextCursor, UI показывает наличие следующей страницы;
постраничная загрузка пока не реализована.

«В эмулятор · инструменты» извлекает именованные Capability из декодированного
состояния устройства (например TextInput). Это заготовки описаний с пустой схемой
аргументов и transport=device-aapi-draft, а не готовый исполнитель. Требуется
описать аргументы и привязать к реальному MCP server_id/server_tool.
Наличие capability в наблюдаемом состоянии не гарантирует права на его вызов.
Автоматического моста device AAPI directives → MCP пока нет.

«Речь»: STT endpoint получает multipart file/model/language и возвращает JSON
с text. TTS endpoint получает JSON model/voice/input/response_format и возвращает
байты аудио. Для провайдеров с другим контрактом нужен отдельный адаптер.

«Студия проверки»: текст → модель, файл → STT, текст → TTS либо полная цепочка
файл → STT → модель → TTS с плеером. Запрошенные моделью инструменты выводятся
отдельно и выполняются только кнопкой пользователя. Результат инструмента пока
не отправляется модели автоматически: многошаговый agent loop не реализован.

## AAPI-интеграция устройства

По умолчанию доступны каркасы SynchronizeStateResponse и RequestStatAck,
либо пользовательские включённые WS-шаблоны.
Экспериментальный aapi_model=true подключает TextInput к модели и возвращает
AliceResponse с текстовой карточкой. В рамках соединения сохраняются последние
6 пар реплик; ResetSession очищает историю.

В разделе «Речь» отдельно включаются:

- aapi_voice: VoiceInput → сборка объявленного канала → STT после Close → модель.
  PCM s16le преобразуется в WAV; Ogg/Opus передаётся в STT как Ogg. Частота и число
  каналов берутся из объявления Format. Аудиоканалы изолированы по соединению.
- aapi_tts: ответ модели → TTS → AliceResponse → TtsSpeak → канальные Ogg/Opus
  страницы → StreamControl.Close. Провайдер должен возвращать Ogg/Opus с EOS;
  MP3 и голый PCM для этой ветки не подходят. Выходные StreamId чётные и уникальны
  в пределах соединения.

Протокольная цепочка проверена на локальных провайдерах и настоящих protobuf-
дескрипторах, но воспроизведение физическим устройством пока не подтверждено.
Распознавание буферизованное, а не потоковый ASR: лимит входа 16 MiB на соединение,
до 4 объявленных каналов, не более 90 секунд сбора по времени поступления.
CancelRequest и новый ввод отменяют текущий запрос провайдера и выходной поток;
при закрытии WS фоновые задачи завершаются. Ошибки доступны в студии по кнопке
«Вызовы и ошибки устройства».

Ответ модели строит агент (движок graph, `agent/`, контракт `docs/contracts/agent.md`):
тред на колонку в `state/agent.sqlite3`, инструменты с классами риска, сценарии как
инструменты, долговременная память владельца колонки (вкладка «Память»,
`docs/contracts/memory.md`). Действия, требующие подтверждения, агент подтверждает голосом («да»/«нет»)
или кнопкой в студии и возвращает результат модели. Полный мост capability → MCP
пока не реализован. Авторизация, push и полный
lifecycle capability остаются отдельными адаптерами.

## Файлы

- runtime.py — общий runtime, состояние, обработчики, провайдеры и API.
- server.py — standalone запуск.
- ui/ — самостоятельный UI, без npm и сборки прокси.
- protocol_import.py — протокол из libquasar_daemons.so станции или zip с .proto / .pb; device_images.py — картинки устройств с сайта умного дома, только по согласию пользователя (в Git их нет, см. docs/setup.md).
- schemas/alice-api.pb, schemas/alica-*.pb — дескрипторы протокола; создаются при первом запуске из загруженного файла протокола.
- state/settings.json и state/handlers.json — переносимый проект эмулятора.
- legacy_replay.py, archive.py — прежний исследовательский SQLite replay,
  сохранённый для совместимости тестов; обычный сервер его базу не открывает.

Тесты из корня проекта: `python -m pytest -q`.
# Пользователи и устройства по SN

Добавлены экраны **HTTP · Quasar** и **Действия устройства**. Первый сохраняет `state.quasar.config` выбранного SN, второй отправляет WS Push в конкретную активную сессию. Список команд, маршруты и границы интеграции с v3rt3p/quasar-server описаны в истории проекта; атрибуция — `NOTICE.md`.

В UI появился раздел «Пользователи и устройства». Создайте пользователя, укажите настоящий серийный номер устройства и свяжите его с наблюдаемыми `DeviceId`. Один владелец может иметь несколько SN. Неизвестные `DeviceId` попадают в непривязанные; IP не используется для определения владельца. Реестр сохраняется в `state/identities.json`.

Профили наследуются: настройки сервера → пользователь → устройство. Поддержаны `system_prompt`, `device_context`, `tools`, `aapi_model`, `aapi_voice`, `aapi_tts`. Состояние хранится отдельно для каждого SN. WS выбирает профиль после `SynchronizeStateRequest.Application.DeviceId`, история и аудиоканалы разделены по соединениям. AI-цепочка отключена для непривязанных устройств. Изменение привязки во время активной сессии запрещено, смена владельца требует `reset_state:true` через API. Изменения профиля применяются при следующем подключении.

`GET /emulator/api/identities` — реестр и активные сессии; `POST` с `X-Emulator:1` — операции `user`, `device`, `state`. HTTP/WS-обработчик может содержать `user_id` и/или `device_sn`; без них он общий. HTTP пока определяет устройство по query `device_id`. Управление локальное, это ещё не система входа и прав доступа конечных пользователей.


## Переключение режима и WS

Маршрут устройства («Эмуляция», «Гибрид», «Прозрачно») меняется сразу, без подтверждения: API `PUT /emulator/api/route_mode` с `{ "sn": "…", "mode": "proxy" }`. Открытые WS-соединения устройства закрываются (close code 1012) только при переходе в «Прозрачно» или из него, колонка переподключается сама; смена `emulate` ↔ `hybrid` соединение не рвёт. HTTP-запросы маршрутизируются заново на каждом запросе. Маршрута по умолчанию нет: устройство без своего маршрута — «Эмуляция».
