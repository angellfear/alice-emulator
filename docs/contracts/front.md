# Фронт TLS

Код: `server_emulator/front.py`.

## Обзор

TCP-фронт публичного TLS-порта: по SNI отдаёт соединение эмулятору, в туннель или отклоняет.

## Обслуживаемые домены и маршрутизация по SNI

Публичный TLS-порт слушает сырой TCP-фронт (`front.py`), а не `TCPSite` напрямую. На каждое
соединение фронт читает ClientHello (до 32 КиБ, без расшифровки) и достаёт SNI. Обслуживаемые
домены (соединение сплайсом уходит внутреннему aiohttp-слушателю с тем же `ssl_context`,
эфемерный порт на 127.0.0.1; накопленные байты идут первыми):

- SNI нет, литеральный IP, имя локальной сети (`.local`) или `server.json local_domain`;
- обязательные `server_config.MANDATORY_DOMAINS` (`quasar.yandex.net`, `rpc.alice.yandex.net`,
  `uniproxy.alice.yandex.net`) — при покрытии DNS-SAN листового сертификата (wildcard ровно на
  один уровень — `cert_covers`, RFC 6125). Обязательный без покрытия соединение отклоняет при
  любом режиме: терминировать нечем, а туннель молча подменял бы эмуляцию настоящим облаком;
- дополнительные «для офлайн и приватности» из `server_config.OPTIONAL_DOMAINS` (`scbh`,
  `clck`, `report.appmetrica`, `push.yandex.ru`, `startup.mobile.yandex.net`,
  `iot.quasar.yandex.ru`), кроме выключенных (`server.json serve_off`);
- домены пользовательского списка `serve_extra` (UI: «Пользовательский список», по одному
  домену на строку, без шаблонов) — тоже при покрытии сертификатом; непокрытый ведёт себя как
  необслуживаемый.

Остальные (например `strm-*.strm.yandex.net`, не покрытый wildcard `*.yandex.net` — из-за
этого колонка не могла открыть TLS к музыке) — решает политика `server.json front_uncovered`:
`tunnel` (по умолчанию) — слепой TCP-туннель к настоящему адресу хоста: A-записи
у внешних DNS (`front_dns`, aiodns), порт публичного слушателя, байт-в-байт, таймауты соединения
и простоя (300 с); адрес самого сервера выкидывается (защита от петли —
`upstream.resolver.local_addresses`), содержимое фронту не видно. `block` — все
необслуживаемые отклоняются: соединение закрывается сразу после чтения SNI, TLS не состоялся.
Сертификат не читается (SAN пуст) — всё сплайсом, списки и политика не применяются.
Хосты авторизации (`passport.yandex.ru`, `oauth.yandex.ru`, суффиксы `.passport.yandex.ru`
и `.passport.yandex.net`) туннелируются всегда — до проверки списков и независимо от
`front_uncovered` (даже `block`): вход и привязка аккаунта идут только в настоящий
Яндекс (экран входа на колонке — WebView паспорта, Chromium отвергает подменный сертификат —
`net_error -213`); для них в журнале уровень info, в замеченных они не
отмечаются. HTTP-порт (80) фронт не обрабатывает. Выключатель `front: false`
возвращает прежний прямой `TCPSite` (без фронта применение тоже требует перезапуска — как прочие
настройки слушателей; хосты авторизации тогда пересылает наверх диспетчер — `endpoints.md`,
«Хосты авторизации»).

Политика (режим и списки) применяется **без перезапуска**: фронт читает `front_uncovered`,
`serve_off` и `serve_extra` из `server.json` на каждое соединение (`front.py::_policy`); уже
открытые соединения не затрагиваются. UI — «Настройки → Сервер»: панель «Обслуживаемые
домены» (обязательные — включены и заблокированы, дополнительные выключаются, пользовательский
список; у каждой строки отметка покрытия сертификатом — зелёный ✓ или красный ✕ с подписью) и
блок «Домены вне сертификата» (два режима и список замеченных); кнопка «Применить» сохраняет
без перезапуска (`api/server-front`). `PUT api/server` эти ключи не обнуляет — форма их не
отправляет, значения берутся из файла.

Реальный адрес колонки сохраняется таблицей `Front.peers` (исходящий сокет сплайса →
оригинальный пир); `serve()` привязывает её к `runtime.client_peer`, и `dispatcher.client_ip`
отдаёт обработчикам настоящий IP вместо 127.0.0.1. Каждый необслуживаемый домен (туннель или
отклонение) фиксируется в `Front.seen` (имя → счётчик, память с запуска фронта) — наружу через
`runtime.front_observed`; имена сертификата — `runtime.front_sans`. Оба отдаёт GET
`api/server-front`; список в UI — с кнопкой «Добавить» (вносит домен в пользовательский список
обслуживаемых). События — в журнал сервера: info о старте (порт, число имён в сертификате),
warning «Домен не обслуживается — соединение идёт туннелем» (адрес в detail, повторы склеивает
журнал), warning «Домен … не обслуживается — соединение отклонено» (режим в detail), error при
неудаче туннеля (DNS, нет адресов после фильтра петли, соединение не прошло). Счётчик туннелей по хостам —
`Front.tunnels` (в памяти) и ×N в журнале. Потоки музыки поставщика (`storage.yandex.net`,
`*.strm.yandex.net`) туннелируются штатно — для них уровень info, а в сообщении общий шаблон
домена (`*.strm.yandex.net`), а не конкретное имя потока: оно меняется на каждый трек
(`strm-mar-NNN` и т.п.), иначе на каждый NNN была бы своя запись журнала.

## Остановка

`Front.stop()` закрывает всё сразу и ничего не ждёт: слушатель закрывается, клиентские сокеты
закрываются, задачи-обработчики соединений отменяются (в `finally` `_connection` закрывает и
стороны туннеля). Ожидать завершения соединений здесь нельзя: туннель может ждать upstream хоть
вечно — `wait_closed()` с живым соединением не заканчивается никогда. Общий проход остановки
сервера (код выхода из `serve()`, `on_cleanup`, дочерние процессы голосового стека) — в
докстринге `control.py`; фронт укладывается в него без собственных ожиданий.
