# Quasar-конфиг: платформенные базовые конфиги + переопределения устройств

Задача (2026-10-25): переработать раздел Quasar-конфига эмулятора. Работаем только
внутри `server_emulator/` — прокси/обсерватория не затрагиваются.

## Как понял задачу

1. **«Маршруты · три состояния» (http_routes) убрать целиком** — код, UI, интеграция
   в dispatch, тесты. Их роль (решать, что делать с неподдержанным маршрутом) теперь
   выполняет каталог эндпоинтов: реплей — эндпоинт, ничего — честный 404.
2. **Раздел Quasar-конфиг становится двухпанельным с боковым меню:**
   - **«Общие конфиги устройств»** — платформенные базовые конфиги. Сверху вкладки,
     каждая вкладка = один JSON-файл платформы (chiron, station_max, yandexstation_2…).
     Внутри — визуальный редактор, собирающий ответ для устройства:
     - **простой вид**: полный парсинг JSON, показываются только значения,
       описанные дескрипторами; контролы (селекторы, тумблеры…) рисуются по правилам
       из JSON — имя, описание, варианты берутся из файла. Пример пользователя:
       subscription = селектор с двумя вариантами (вкл/выкл); выбор подставляет
       нужное значение (поддерево) в тело;
     - **полный вид**: редактирование самого JSON-файла; слева — граф-дерево,
       выбор ветви открывает её в редакторе; подсказки — шаблоны с автовставкой
       по клику.
   - **«Переопределение под устройство»** — слева вертикальный список устройств
     (унифицированный с вкладкой «Устройства»: картинка модели, статус), при выборе —
     редактор, где видны **только добавленные переопределения**.
     Переопределение значения — 2 варианта: (1) вариант из дескриптора JSON
     платформы, (2) своё значение / вызов базы / код.
     Добавление — 2 способами: (1) из списка редактируемого по дескрипторам
     платформы, (2) путь к объекту вручную (тогда только «своё значение» или
     «код/база»).

## Архитектура

### 1. Файл платформы — `state/quasar/platforms/<platform>.json`

Один файл описывает и базовое тело, и редактор. Два корневых ключа:

```json
{
  "platform": "chiron",
  "title": "Станция с экраном (chiron)",
  "description": "Базовый ответ /get_sync_info для платформы chiron",
  "sync": { "...": "полное базовое тело ответа: config/tags/glagol/subscription/…" },
  "controls": [
    {
      "path": "subscription.enabled",
      "type": "select",
      "label": "Подписка",
      "hint": "Состояние подписки Алисы для устройств платформы",
      "options": [
        {"value": true, "label": "Включена",
         "patch": {"subscription": {"enabled": true, "disabled_reason": null}}},
        {"value": false, "label": "Выключена (invalid_subscription_user)",
         "patch": {"subscription": {"enabled": false, "disabled_reason": "invalid_subscription_user"}}}
      ]
    },
    {"path": "tags", "type": "text-list", "label": "Теги", "hint": "…"},
    {"path": "config.device_config.name", "type": "text", "label": "Имя устройства",
     "value_hint": "подставляется имя из реестра, если не задано явно"}
  ]
}
```

Ключевые решения:

- **`options[].patch` — поддерево, а не скаляр**: вариант селектора меняет столько
  полей, сколько нужно (пара enabled + disabled_reason меняется вместе). Это
  обобщение примера пользователя «селектор подставляет нужное значение в тело».
- **Типы контролов**: `select` (варианты с patch), `toggle` (сахар: select из двух
  вариантов вкл/выкл), `text`, `number`, `text-list`, `code` (см. «Источники
  значений»), `db`. Набор расширяемый — контрол описан данными, UI рендерит по `type`.
- **`path`** — точечный путь в `sync`; текущее значение контрола в простом виде
  читается из базового тела (нет отдельного хранилища «значений контролов» —
  тело и есть состояние, контролы — только правила отображения/правки).

### 2. Источники значений (динамика) — один движок

Переиспользуем плейсхолдеры каталога эндпоинтов (`endpoints.TOKENS`), никакого
второго синтаксиса. Везде, где ожидается значение (лист `sync`, patch, override),
допустима строка с токенами + три специальных источника (решения по ответам):

- `{"expr": "{{now_iso}}"}` — шаблон на момент запроса. Контекст: запросные
  `now/now_ms/now_iso/uuid` (из endpoints) + токены реестра эмулятора:
  `{{device_id}}`, `{{device_name}}`, `{{platform}}`, `{{user_id}}`,
  `{{user.name}}`, `{{user.location.city}}`, `{{device.room}}`,
  `{{device.fields.<ключ>}}`, `{{user.fields.<ключ>}}`;
- `{"db": "<точечный путь>"}` — **значение из БД эмулятора** (реестр): корни
  `user.` (name/location/fields) и `device.` (name/room/fields/state). Даёт
  целые объекты/массивы (когда токен-строка неудобна);
- `{"run": "<команда>"}` — **запуск внешнего скрипта/exe сервером** (не eval):
  subprocess с таймаутом ~3 с; stdout → значение (если парсится как JSON —
  структура, иначе строка с тримом); переменные окружения QSN/QDEVICE_ID/
  QUSER_ID/QPATH/QCONTEXT(json) передают контекст; ошибка/таймаут — значение
  базового тела остаётся, инцидент пишется в runtime.recent. В UI — поле
  команды с подсказкой формата.

### 3. Переопределения устройств

Хранятся в реестре устройства: `device.state.quasar_overrides` —
`[{"path": "config.device_config.name", "source": {...}, "notes": ""}]`, где
`source` — либо `{"option": "<id варианта из контрола платформы>"}`, либо явное
значение/`expr`/`call`/`db` (как выше). Переживает рестарты, виден в существующем
API identities.

Композиция ответа `/get_sync_info` (quasar.py):

```
base(платформа устройства)  →  применить overrides по path (deep-set)  →  рендер
динамических источников  →  {status: ok, **результат}
```

Платформа устройства берётся из `device.profile.platform`, при отсутствии —
`default` платформа (файл с флагом `"default": true`; fallback — первый файл).

### 4. API (admin, `/emulator/api/…`)

- `quasar_platforms`: GET — список с метаданными (платформа, title, default,
  число контролов); GET `?platform=` — файл целиком; PUT — сохранить файл
  (валидация: структура, пути контролов существуют в sync — предупреждением);
  DELETE `?platform=`.
- Переопределения — через существующий `identities` (state), UI пишет
  `quasar_overrides` в состояние устройства.
- `http_routes` — действие и модуль удаляются (решение: насовсем).

### 5. UI (вкладка «HTTP · Quasar» → «Quasar»)

```
┌───────────────┬──────────────────────────────────────────────────────┐
│ ◉ Общие       │ [chiron] [station_max] [yandexstation_2] [＋]        │
│   конфиги     │ ┌ Простой ─┬ Полный ────────────────────────────────┐ │
│               │ │ простой: контролы платформы (label/hint/значение) │ │
│ ○ Переопреде- │ │   из controls + текущего тела                     │ │
│   ление под   │ │ полный: [дерево-граф sync] [редактор ветви JSON]  │ │
│   устройство  │ │   + чипы-шаблоны (клик = автовставка)             │ │
└───────────────┴──────────────────────────────────────────────────────┘
```

- **Сайдбар**: два пункта (Общие конфиги / Переопределения). Стили — как табы
  панели, вертикально.
- **Общие конфиги**: вкладки платформ сверху («＋» — новая: копия текущей/пустая).
  Простой вид — карточки контролов (селектор/тумблер/поля), сохранение = патчи
  применяются к `sync` и файл уходит PUT'ом. Полный вид — слева дерево JSON
  (`sync` + `controls`; выбор ветви — редактор её поддерева), справа textarea
  выбранной ветви; чипы-подсказки: `{{now_iso}}`, `{"call":"uuid4"}`,
  `{"db":"ключ"}` — клик вставляет в позицию курсора.
- **Переопределения**: слева список устройств — унифицируем с вкладкой
  «Устройства» (общий модуль `devices_common.js`: modelBySn/картинка/статус/IP);
  справа: список override'ов этого устройства, «＋ добавить» — выбор из
  дескрипторов платформы устройства или «путь вручную» (тогда редактор значения
  только «своё значение» / expr/call/db). Каждый override: путь, источник-редактор
  по типу, удалить.

### 6. Удаление http_routes

- `server_emulator/http_routes.py` — удалить; `runtime.py`: вырезать init,
  ветку dispatch (TransparentRoute, note), импорты; `backend.js`: функции
  `routesApi`/`routes` и секцию UI; тест `tests/test_http_routes.py` — удалить,

### 7. Миграция живых данных

- Из текущих `state.quasar` устройств (залитые capture-конфиги): платформа
  устройства определяется по заголовкам из дампов/`profile.platform`; для каждой
  платформы первый (эталонный) device-конфиг становится базой файла платформы
  (одноходовая миграция выполнена в исходном проекте; скрипт в репозиторий не входит); расхождения конфигов других устройств
  той же платформы (имена, сертификаты, ids) — их overrides.
- Старое поле `state.quasar` после перехода не читается (композиция новая);
  хранится как backup-ключ `quasar_legacy` один релиз.

### 8. Порядок работ

1. Удаление http_routes (код, UI, тесты) — освобождает место и вкладку.
2. Модель: формат платформы + валидатор + хранилище + sources-движок
   (expr/call/db поверх endpoints-рендера) — юнит-тесты.
3. Композиция в quasar.py get_sync_info + тесты (base/override/select-patch/
   динамика/платформенный fallback).
4. API quasar_platforms/quasar_values + тесты.
5. Сид-миграция живых конфигов в платформы/overrides.
6. UI: сайдбар → общие конфиги (простой/полный с графом) → переопределения
   (унификация списка устройств).
7. Полный suite, рестарт, живая проверка на колонках (sync 200, контент
   идентичен текущему до вчитывания отличий).

## Решения (ответы 2026-10-25)

1. http_routes — **удаляем насовсем**.
2. «Исполнение кода» — **запуск внешнего скрипта/exe сервером** (`run`), не eval.
3. «Вызов базы» — **поля из БД эмулятора**: секции пользователя и устройства
   (реестр), через `db`-путь и токены `{{user.*}}`/`{{device.*}}`.
4. Миграция — **автоматическая** из текущих залитых конфигов.

## Слой аккаунта (TASK-047, 2026-10-31)

Основание — разбор источников ответа: на настоящем сервере `config` собирается из частей
с разными владельцами — `account_config` (аккаунт, меняется из приложения), `device_config`
(устройство), `system_config` (сервер, снаружи не пишется). Эмулятор повторяет это владение слоем
переопределений владельца.

### Порядок слоёв `/get_sync_info`

```
common → merge-patch платформы → переопределения аккаунта → переопределения устройства
       → инлайн-узлы ($select/$string/…) → динамика ({{токены}} / db / run)
```

Устройство сильнее аккаунта: одно и то же значение, заданное в обоих слоях, берётся из
переопределения устройства. Платформа слабее аккаунта: аккаунт всегда поверх патча платформы.

### Хранение и формат

- У пользователя реестра (`identities`) — список `quasar_overrides` того же формата, что у
  устройства: `[{"path": "...", "source": ...}]`; `source` — литерал / `{"expr"}` / `{"db"}` /
  `{"run"}` / `{"delete": true}` / `{"$select": "вариант"}`.
- **Путь хранится полным**, от корня ответа: `config.account_config.spotter` (решение TASK-047).
  Полный путь совпадает с путями устройства и ключами `trace`; UI показывает и принимает путь
  внутри `account_config` и добавляет префикс сам.
- Допустимы только пути глубже `config.account_config` (сам узел целиком не заменяется). Путь вне
  этой части — `QuasarConfigError` (в `compose`) / `ValueError` при сохранении (HTTP 400).
- Физически — запись meta `identity_user_quasar` хранилища (`{user_id: [...]}`), как у групп
  стереопар: схема таблицы `users` не менялась. В представлении реестра (`GET identities`) —
  поле `quasar_overrides` пользователя (ключа нет, если список пуст). Правка имени пользователя
  слой не трогает; удаление пользователя удаляет и слой.
- У устройства без владельца слоя аккаунта нет (`/get_sync_info` такому устройству и так отвечает
  403 `device_not_assigned`; в просмотре итогового конфига слой не применяется).

### API

- Чтение — `GET /emulator/api/identities` (`users[].quasar_overrides`).
- Запись — `POST /emulator/api/identities` `{"operation": "user_quasar_overrides", "id": "<user>",
  "quasar_overrides": [{path, source}, …]}`; список заменяется целиком, пустой — очищает слой.
- `GET /emulator/api/quasar_composed?device=SN` учитывает слой аккаунта; в `origins` значения
  подписаны «аккаунт <имя пользователя>» (для `delete`/`$select`/`expr`/`db`/`run` — «аккаунт <имя>
  (<вид>)»); если значение затем перекрыто устройством — «переопределение устройства».

### UI

Карточка пользователя («Пользователи → Параметры»), вкладка «Настройки аккаунта»: список
переопределений, диалог добавления/правки (источник — те же виды, что у устройства), сохраняется
общей кнопкой «Сохранить» диалога.

### `account_config` в патчах платформ

Решение: оставить. Блок `account_config` в `platforms/*.json` (например,
`chiron.json: account_config.informers_enabled`) — значения по умолчанию для платформы; запрета нет.
Аккаунт их переопределяет, устройство переопределяет аккаунт.


## Источник конфига устройства (TASK-052)

Каждое устройство выбирает, откуда брать ответ на `GET /get_sync_info`. Режим хранится в
`state.quasar_source` устройства, свой ответ — в `state.quasar_custom`, последний ответ Яндекса —
в `state.quasar_direct_last` (`{ts, status, body}`, тело — распакованный JSON). Отсутствие поля —
режим `generated`.

| Метка | Режим | Что получает колонка |
|---|---|---|
| **Генерируемый** | `generated` (по умолчанию) | конфиг, собранный `compose` (слои 1–6, см. выше) |
| **Напрямую** | `direct` | ответ настоящего `quasar.yandex.net` без изменений; обмен — в «Журнал» (`source=upstream`); успешный JSON сохраняется в `state.quasar_direct_last` |
| **Свой** | `custom` | `state.quasar_custom` как есть: без слоёв, инлайн-узлов и подстановки стереопары; нет сохранённого или в нём нет `config` → 409 `quasar_custom_not_set` |

Маршрут API (`ui/api/quasar_config_api.py`, домен `quasar_source`):

- `GET ?sn=` → `{mode, direct_last, custom, can_fetch}`; `can_fetch` — запомнены ли заголовки
  последнего опроса этой колонки;
- `PUT {sn, mode?, custom?}` — сохранение режима и/или своего ответа под `runtime.lock`
  (custom — JSON-объект с объектом `config`, иначе 400);
- `POST {sn, action: "generate"}` — ответ, который собрал бы `compose` (как отдаётся колонке,
  включая `group`); ничего не сохраняет;
- `POST {sn, action: "fetch"}` — запрос оригинальному серверу с запомненными заголовками и query
  этой колонки; тело ответа возвращается, ничего не сохраняет; заголовков нет → 409.

Заголовки последнего `get_sync_info` каждого устройства (включая `Authorization`) запоминаются
**только в памяти** `runtime` (по SN), в любом режиме опроса; на диск и в state не пишутся. При
маршруте устройства «Прокси»/«Запись» (TASK-044) запросы и так идут в Яндекс — источник конфига
не применяется, в панели переключатель неактивен. Тесты: `tests/test_quasar_source.py`.
